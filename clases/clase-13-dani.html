Stacking: Cache + Batch = 95% de ahorro en input

Los multiplicadores de caching y batch se acumulan. Un token cacheado dentro de un batch se cobra a:

0.10 × 0.50 = 0.05 = 5% del precio original

Para pipelines de análisis masivo con contexto compartido (misma base de código, mismas instrucciones), el sistema prompt puede costar 20× menos que sin optimizaciones.

🔑 Conceptos clave

Tokens

1 token ≈ 4 caracteres / 0.75 palabras. Todo lo que envías es input; todo lo que Claude responde es output. Los tokens de output cuestan 5× más que los de input en todos los modelos actuales.

Prompt Caching

Reutiliza porciones procesadas del prompt (system, docs, tools) entre llamadas. Cache hit = 10% del precio de input. TTL de 5 minutos (write 1.25×) o 1 hora (write 2×).

Context Windows

Sonnet 4.6 y Opus 4.6+ soportan hasta 1M tokens al mismo precio por token. Sin caching, el historial completo de conversación se cobra en cada turno.

Selección de modelos

Haiku para tareas simples de alta frecuencia, Sonnet como default de producción, Opus solo para razonamiento complejo. Usar el modelo incorrecto puede costar 5× de más.

Message Batches API

Procesamiento asíncrono con 50% de descuento fijo en todos los modelos. Hasta 100,000 requests o 256 MB por batch. La mayoría finaliza en menos de 1 hora.

Monitoreo de costos

Tracking de usage.cache_read_input_tokens, distribución por modelo, costo por feature. Herramientas: Helicone, LangSmith, LiteLLM, Langfuse.

Módulo 1: Entender los tokens y su costo real

⏱ 20 min · Fundamentos

Antes de optimizar, hay que medir. El campo usage en cada respuesta de la API contiene los datos exactos de consumo. La mayoría de los devs no lo instrumentan desde el inicio y se enteran del sobrecosto cuando llega la factura.

  • Anatomía de los tokens: system prompt, historial de conversación, definiciones de tools, overhead del modelo
  • Por qué el historial crece exponencialmente sin caching: el mensaje 20 envía los 19 anteriores
  • Cómo leer input_tokens, output_tokens, cache_read_input_tokens
  • Calcular el costo exacto de cada llamada en USD desde el código
  • Overhead de tools: Sonnet 4.6 con auto agrega 497 tokens al system prompt automáticamente
  • Regla de oro: los tokens de output cuestan 5× más que los de input → prompts precisos, respuestas enfocadas = ahorro doble

Módulo 2: Prompt Caching — de la teoría al código

⏱ 25 min · Técnicas avanzadas

El prompt caching es la optimización con mayor impacto para la mayoría de aplicaciones. Si tienes un system prompt largo, documentos de contexto o una base de código que Claude necesita analizar repetidamente, el caching puede reducir tu factura un 90% en esas porciones.

  • Cache explícito: añadir cache_control: {"type": "ephemeral"} a bloques específicos del system prompt
  • Cache automático: aplicar cache_control a nivel de request para conversaciones multi-turno
  • Cache de 1 hora: {"type": "ephemeral", "ttl": "1h"} para workflows agénticos con pasos espaciados
  • Mínimos de tokens: 1,024 para Sonnet 4.6 · 4,096 para Haiku 4.5 · 1,024 para Opus 4.8
  • Pre-warming: usar max_tokens: 0 para cargar el caché antes de que lleguen usuarios
  • Error clásico: colocar el breakpoint en contenido que cambia cada request → cache miss garantizado
  • Hasta 4 breakpoints de caché por request; jerarquía: tools → system → messages
# Implementación mínima de prompt caching (Python)
import anthropic
client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": SYSTEM_PROMPT_EXTENSO,  # > 1,024 tokens
            "cache_control": {"type": "ephemeral"}  # ← la clave
        }
    ],
    messages=[{"role": "user", "content": codigo_del_usuario}]
)

# Verificar que el caché funcionó
u = response.usage
print(f"Cache reads:  {u.cache_read_input_tokens}")   # > 0 = ahorro activo
print(f"Cache writes: {u.cache_creation_input_tokens}")  # > 0 = caché creado

Módulo 3: Selección de modelos y Message Batches API

⏱ 25 min · Optimización avanzada

Routing inteligente entre modelos y uso del Batches API son las dos palancas que, combinadas con caching, permiten llegar al 95% de ahorro en casos de uso de procesamiento masivo.

  • Routing por complejidad: Haiku para clasificación/extracción (3× más barato que Sonnet), Opus solo cuando se justifica (reservar para arquitectura y razonamiento complejo)
  • Ejemplo real: 10,000 clasificaciones/día con Haiku vs. Sonnet = $5/día vs. $15/día = $300/mes de ahorro solo por elegir el modelo correcto
  • Message Batches API: 50% de descuento fijo, sin umbral de volumen, en todos los modelos
  • Límites del batch: hasta 100,000 requests o 256 MB; la mayoría procesa en <1 hora
  • Stacking: cache hit dentro de un batch = 10% × 50% = 5% del precio original
  • Casos de uso ideales para batch: revisiones de código en CI/CD, generación de tests, análisis de PRs, documentación, clasificación de issues
  • Polling del estado del batch vs. webhooks; manejo de errores parciales por request

Módulo 4: Monitoreo de costos en producción

⏱ 20 min · Observabilidad

El monitoreo convierte las optimizaciones de teoría en práctica sostenible. Sin visibilidad, el equipo no puede saber si las optimizaciones funcionan ni detectar regresiones de costo.

  • Métricas clave: costo por request, cache hit rate, distribución por modelo, tokens de output promedio, costo por feature/endpoint
  • Helicone: integración en 1 línea cambiando la base_url del cliente — todas las llamadas existentes funcionan sin modificación
  • LiteLLM: presupuestos por clave API o equipo, rechazo automático al superar el límite, configuración en YAML
  • Instrumentación manual: capturar usage en cada llamada y enviar a DataDog, Grafana o cualquier sistema de métricas
  • Alertas: configurar umbrales de gasto diario/mensual antes de escalar a producción
  • Anthropic Console: breakdown de uso oficial por modelo, ideal para auditorías y revisión de facturas
💪 Ejercicio práctico

Implementar prompt caching y medir el ahorro real

Objetivo: Construir un analizador de código con y sin caching, ejecutarlo 5 veces de cada modo con el mismo system prompt, y documentar el ahorro real en tokens y USD.

Paso 1 — Setup (10 min)

  1. Instalar el SDK: pip install anthropic
  2. Exportar la clave: export ANTHROPIC_API_KEY="sk-ant-..."
  3. Crear un system prompt de más de 1,024 tokens (instrucciones de revisión de código detalladas)

Paso 2 — Comparar llamadas con y sin cache (20 min)

  1. Implementar analizar_sin_cache() — system prompt como string plano
  2. Implementar analizar_con_cache() — system prompt con cache_control
  3. Ejecutar cada función 5 veces y registrar tokens + costo USD por llamada
  4. Calcular el ahorro total y el porcentaje de reducción
  5. Proyectar el ahorro a 1,000 llamadas/día y a 30 días

Paso 3 — Bonus: Message Batches API (30 min)

  1. Enviar las 5 revisiones como un batch usando client.messages.batches.create()
  2. Comparar el costo del batch vs. llamadas síncronas
  3. Medir la latencia del batch (tiempo hasta que processing_status == "ended")
  4. Discutir: ¿qué workloads de su app actual podrían batchearse sin afectar la UX?

Reflexión grupal (10 min): Cada participante comparte qué system prompt de su aplicación actual podría cachear hoy mismo y cuánto estima que ahorraría.
