🔑 Conceptos clave

¿Qué es Spec Driven Development?

SDD es una metodología donde se redacta una especificación estructurada —que define intención, comportamiento, restricciones y criterios de aceptación— antes de escribir una sola línea de código. La aparición de LLMs como Claude lo hace práctico y escalable a nivel individual.

La diferencia con el "vibe coding" es fundamental: SDD separa la fase de diseño de la implementación, manteniendo al humano como arquitecto y árbitro de decisiones.

Documentos del ecosistema SDD

Documento Propósito ¿Quién lo escribe?
PRD Define el "qué" y el "por qué". Audiencia, problema, métricas de éxito. Product Manager / Dev
SPEC.md Especificación técnica: interfaces, flujos, edge cases, criterios de aceptación. Developer + Claude (iterativo)
PLAN.md Plan paso a paso: archivos a modificar, orden, dependencias. Claude (revisado por dev)
TDD Casos de prueba definidos antes de implementar. Se convierte en la suite. Developer + Claude
CLAUDE.md Contexto permanente del proyecto: stack, convenciones, comandos. Developer (en git)

BDD: criterios de aceptación Given / When / Then

Estos criterios van directamente en el SPEC.md y Claude los usa como guía para saber qué construir y cuándo terminó:

Given el usuario está autenticado y tiene rol "admin"
When hace POST /api/properties con datos válidos
Then la propiedad se guarda, se retorna 201 y se dispara el evento "property.created"

CLAUDE.md: la "constitución" del proyecto

Claude lee CLAUDE.md al inicio de cada sesión. Es la diferencia entre un asistente genérico y un pair programmer que conoce tu proyecto:

# Mi Proyecto

## Stack
- Next.js 14, TypeScript, Prisma, PostgreSQL
- Tests: Vitest + Playwright para E2E

## Convenciones
- Usar ES modules (import/export), nunca require
- Nombres de archivos en kebab-case
- Commits convencionales: feat:, fix:, chore:

## Comandos clave
- npm run dev       → servidor local
- npm run test      → vitest watch
- npm run typecheck → tsc --noEmit

Regla de oro: si Claude sigue haciendo algo incorrecto a pesar de tener la instrucción, el CLAUDE.md está demasiado largo. Podarlo es mantenimiento activo — cada línea debe justificarse.

Por qué SDD reduce alucinaciones

Ancla de contexto

Un spec bien escrito reduce la ambigüedad — el modelo sabe exactamente qué construir y con qué restricciones.

Validación automática

Si el output no cumple el spec, el CI/CD falla. El spec se convierte en una puerta de calidad automatizable.

Coherencia entre sesiones

Claude no "olvida" decisiones previas porque están escritas en el spec y en CLAUDE.md — accesibles en cada sesión.

Revisión trazable

El spec es la fuente de verdad, no los comentarios del código. Los PRs se pueden revisar contra el spec original.

💪 Ejercicio práctico

Convertir un feature request en lenguaje natural → SPEC.md → PLAN.md → código implementado con tests. Duración estimada: 45–60 min.

Punto de partida: feature request de ejemplo

Como usuario autenticado,
quiero poder guardar propiedades en favoritos
para revisarlas más tarde sin tener que buscarlas de nuevo.
  1. 1
    Genera SPEC.md con Claude

    Pide a Claude que actúe como tech lead y escriba el spec completo con criterios de aceptación, interfaces TypeScript, endpoints de API y scope explícito. Itera hasta que el spec esté preciso.

  2. 2
    Valida el SPEC.md

    ¿Qué problema resuelve? ¿Cuáles son los criterios de éxito medibles? ¿Qué está fuera del scope? ¿Tiene sentido técnico dado el stack?

  3. 3
    Genera PLAN.md desde el spec

    Claude lista los archivos a crear o modificar, el orden de cambios, migraciones de DB si aplica, y los tests a escribir por cada criterio de aceptación.

  4. 4
    Implementa con Claude Code CLI

    Modo plan primero — Claude muestra el plan antes de codear. Ejecuta tests al finalizar y corrige si fallan. Usa claude "implementa la feature de favoritos..."

  5. 5
    Validación adversarial

    Subagente en sesión nueva revisa la implementación contra el SPEC.md. Lista gaps sin incluir preferencias de estilo. Solo reporta lo que afecta correctitud.

  6. 6
    Commit atómico

    Mensaje de commit convencional que referencia el spec. Ejemplo: feat(favorites): implement save/unsave property — resolves SPEC-04

Entregable: PLAN.md
Entregable: Código + Tests
Entregable: Commit
