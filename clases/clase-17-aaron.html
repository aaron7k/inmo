⏰ Agentes cronometrados para ejecución de tareas programadas

Construye pipelines de IA que se ejecutan solos, fallan de forma segura y se monitorean en tiempo real

👤 Aaron 📅 Viernes 14 agosto 2026 👥 Devs + Ops ⏱ 90 minutos 🏷 Clase 17
🎯 Objetivos
  • 1
    Diseñar agentes que se ejecuten solos en horarios definidos con expresiones cron, sin requerir intervención humana en cada ciclo.
  • 2
    Elegir la herramienta de scheduling correcta según el contexto: schedule library, APScheduler, Celery Beat, GitHub Actions o AWS EventBridge.
  • 3
    Integrar la API de Claude en pipelines cronometrados para que el agente analice datos, tome decisiones y actúe de forma autónoma.
  • 4
    Implementar idempotencia y manejo de fallos para que el agente sea seguro de re-ejecutar sin efectos secundarios duplicados.
  • 5
    Instrumentar observabilidad completa: logs estructurados, métricas en Grafana y alertas que detecten fallos silenciosos antes de que impacten al negocio.
🔑 Conceptos clave
TérminoDefinición
Cron JobTarea programada que se dispara según una expresión de tiempo estándar (5 campos). El estándar POSIX adoptado por casi todas las plataformas modernas.
Expresión cronCadena de texto que define el horario: 0 9 * * 1-5 = "cada día hábil a las 9 am". Soporta wildcards (*), rangos, pasos y listas.
Agente cronometradoAgente de IA que recibe un disparador temporal, ejecuta un workflow autónomo (consultar → razonar → actuar → reportar) y termina limpiamente hasta el próximo ciclo.
IdempotenciaPropiedad que garantiza que ejecutar la misma tarea múltiples veces produce el mismo resultado que ejecutarla una sola vez. Crítico cuando hay reintentos.
At-least-once deliveryGarantía de los brokers de mensajes: el mensaje se entrega como mínimo una vez, pero podría entregarse más. Requiere que el consumidor sea idempotente.
Dead Letter Queue (DLQ)Cola donde van las tareas que fallaron todos sus reintentos. Permite inspección post-mortem sin perder datos.
Event-driven schedulingEl agente se dispara por un evento (nuevo archivo, webhook, mensaje en cola) en lugar de por tiempo. Complementa al cron cuando la cadencia es irregular.
JitterDesplazamiento aleatorio añadido al horario para evitar que miles de workers arranquen exactamente al mismo segundo (thundering herd problem).
Backfill / Catch-upCapacidad de re-ejecutar todas las ejecuciones perdidas durante un período de downtime. Algunos schedulers lo hacen automáticamente al reiniciar.
ObservabilidadCapacidad de entender el estado interno de un sistema a partir de sus salidas externas: logs, métricas y trazas distribuidas (los tres pilares).
Scheduler persistenceEl estado del scheduler se guarda en base de datos o Redis, sobreviviendo reinicios de la aplicación sin perder jobs programados.
Tarea huérfanaJob que quedó corriendo pero sin worker activo que lo supervise. Requiere TTL y monitoreo de heartbeat para detectarlos.

Módulo 1: Fundamentos de cron
0 – 20 min

Anatomía de una expresión cron y los patrones de scheduling para sistemas de IA. Por qué el cron es el contrato más simple y confiable entre el tiempo y el código.

# Anatomía de una expresión cron (5 campos)
┌──── minuto (0-59)
│ ┌─── hora (0-23)
│ │ ┌── día/mes (1-31)
│ │ │ ┌─ mes (1-12)
│ │ │ │ ┌ día/sem (0-7)
│ │ │ │ │
* * * * *
ExpresiónSignificado
*/5 * * * *Cada 5 minutos
0 * * * *Cada hora en punto
0 9 * * 1-5Días hábiles a las 9 am
0 0 1 * *Primer día de cada mes
30 14 * * 3Miércoles a las 14:30
Reglas de oro: GitHub Actions siempre corre en UTC. El mínimo en GitHub Actions es 5 minutos; en Claude Code Routines es 1 hora. Nunca usar * * * * * con agentes de IA — los costos de API se disparan. Siempre agregar jitter en producción.
  • Cron vs. event-driven: cuándo usar cada patrón
  • Diferencias entre cron del sistema operativo, APScheduler y servicios cloud
  • El problema del thundering herd y cómo el jitter lo resuelve
  • Herramienta recomendada: crontab.guru para validar expresiones

│
▼ (disparo temporal)
AGENTE WRAPPER
├── 1. Verificar idempotencia (¿ya corrió hoy?)
├── 2. Recolectar datos (API / DB / archivos)
├── 3. Llamar Claude API → análisis + decisión
├── 4. Ejecutar acciones (email, Slack, DB write)
├── 5. Guardar estado de ejecución
└── 6. Emitir métricas y logs estructurados
Patrones de scheduling para agentes:
Cron fijo
Reportes diarios, resúmenes nocturnos. Herramienta: APScheduler, GitHub Actions.
Intervalo adaptivo
Monitoreo que duerme más cuando hay calma. Claude elige el intervalo dinámicamente.
Event-driven
Procesar al instante cuando llega nuevo dato. EventBridge + Lambda.
Daisy-chain
Agente A pasa resultado a Agente B. Celery chains, Step Functions.
One-shot diferido
Recordatorios, acciones retrasadas. APScheduler one-shot, CronCreate.
# APScheduler 4.x + Claude API — patrón base
from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger
import anthropic

cliente = anthropic.Anthropic()

async def agente_metricas():
  run_id = datetime.utcnow().strftime("%Y%m%d-%H")
  if ya_ejecutado(run_id): return
  metricas = obtener_metricas()
  respuesta = cliente.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": f"Analiza: {metricas}"}]
  )
  analisis = json.loads(respuesta.content[0].text)
  if analisis["anomalia"]: enviar_alerta(analisis)
  marcar_ejecutado(run_id, analisis)

scheduler = AsyncIOScheduler()
scheduler.add_job(agente_metricas, CronTrigger(minute=0),
  misfire_grace_time=300, coalesce=True)
Módulo 3: Manejo de fallos y resiliencia
50 – 70 min

Los 5 modos de fallo de un agente cronometrado y cómo blindar cada uno. Idempotencia distribuida con Redis, retry con backoff, DLQ con Celery.

  • Fallo silencioso: el agente termina sin error pero no hizo nada. Requiere heartbeat y validación de salida.
  • Timeout: la llamada a Claude demora más de lo esperado. Envolver siempre con asyncio.wait_for().
  • Fallo de idempotencia: el agente se ejecuta dos veces y duplica envíos. Usar lock Redis (SET NX EX).
  • Rate limit de API: Claude rechaza la petición. Implementar retry con exponential backoff + jitter.
  • Fallo de la máquina: el servidor cae a mitad de la tarea. Requiere persistencia de estado y catch-up.
# Idempotencia con Redis — patrón lock distribuido
r = redis.Redis(host="localhost", port=6379)

def ejecutar_si_no_fue(run_id: str, ttl: int = 3600):
  lock_key = f"agente:lock:{run_id}"
  return r.set(lock_key, "1", nx=True, ex=ttl)

# Celery con DLQ y reintentos
@app.task(max_retries=3, acks_late=True,
  dead_letter_exchange="agentes-dlq")
def tarea_agente(self, run_id):
  try:
    ejecutar_agente(run_id)
  except Exception as exc:
    raise self.retry(exc=exc,
      countdown=2 ** self.request.retries)
Checklist de resiliencia:
  • Timeout en todas las llamadas externas (Claude, APIs, DB)
  • Retry con backoff exponencial + jitter en rate limits
  • Idempotencia via Redis NX o unique constraint en DB
  • DLQ para inspección de fallos permanentes
  • Heartbeat: el agente emite "estoy vivo" cada N minutos
  • Alerta si no hay heartbeat en 2x el intervalo esperado
  • Coalesce habilitado: si se perdieron varios disparos, ejecutar solo uno

💪 Ejercicio práctico

Agente de análisis horario con reporte por email

Construye un agente Python que corra cada hora, analice métricas simuladas usando Claude API, y genere un reporte cuando detecte una anomalía.

30 min · En parejas Python 3.10+ anthropic + schedule
Paso 1 — Instalar dependencias:
pip install anthropic schedule
Paso 2 — Agente base:
import anthropic, json, random, schedule, time
from datetime import datetime

cliente = anthropic.Anthropic()

def simular_metricas():
  return {
    "cpu_pct": random.uniform(20, 95),
    "memoria_pct": random.uniform(40, 92),
    "latencia_ms": random.uniform(80, 800),
    "errores_por_min": random.randint(0, 15)
  }

def analizar_con_claude(metricas):
  r = cliente.messages.create(
    model="claude-sonnet-4-5", max_tokens=512,
    messages=[{"role": "user",
      "content": f"Analiza en JSON {{'anomalia': bool, 'severidad': str, 'resumen': str}}: {metricas}"}]
  )
  return json.loads(r.content[0].text)

def ejecutar_ciclo():
  m = simular_metricas()
  a = analizar_con_claude(m)
  if a["anomalia"]: print(f"ALERTA: {a['resumen']}")

schedule.every().hour.do(ejecutar_ciclo)
ejecutar_ciclo() # Primera ejecución
while True: schedule.run_pending(); time.sleep(30)
Criterios de evaluación:
  • El agente corre sin errores y produce output estructurado
  • Claude responde con JSON válido y análisis coherente
  • El agente detecta correctamente el caso de alerta vs. normal
  • Los logs incluyen timestamp, run_id y duración del ciclo
Extensiones para los más rápidos:
  • Agregar persistencia del historial en un archivo JSON
  • Implementar idempotencia con un set de run_ids ya ejecutados
  • Migrar de schedule a APScheduler con persistencia SQLite
